## What the homepage SSR actually does per request

`frontend/app/page.tsx` before this work:

1. `export const dynamic = "force-dynamic"` — Next disables all caching.
2. `await auth()` — reads NextAuth JWT cookie. Fast, but marks the render dynamic.
3. `await fetch(BACKEND/api/get_feed?limit=1, {cache: 'no-store', X-User-Id})` — 1 Redis pipeline
   (ZREVRANGE + HGETALL + SMEMBERS) on the backend. ~5ms.
4. React server-render `<PageWrapper><FeedClient initialFeed={feed} .../></PageWrapper>`.
   `FeedClient` is `'use client'` (lazy Tribonacci feed). `PageWrapper` renders the shell.

The **big cost is step 4** — the React render + serialization of the initial
tree, which is what dominates the 636ms under load. Fetches complete in ~5ms.
Every render is identical for anonymous visitors between scribe cycles
(69 min), so it is the obvious ISR candidate.

## Gunicorn RSS math + why workers stay where they are

Running config: **20 workers × 8 threads × `--preload`**, port 5005.

- 21 processes (20 workers + master), ~442 MiB avg RSS each, **~9.3 GiB total RSS**.
- With `--preload`, code pages are shared copy-on-write, so PSS is lower than that
  — but each worker holds its own Solr/Redis connection state that grows.
- Free RAM (with Redis at only 311 MiB of its 16 GiB cap): 8.3 GiB. If Redis grew
  to its cap, headroom would be tight.

Under test (a): **no worker exceeded 5% CPU**. Flask is not the throttle — the
Next.js layer serves at 76 req/s regardless. 8 threads per worker × 20 workers =
160 concurrent Flask request slots for 1.4 req/s of real demand.

**Recommendation: leave gunicorn at current config for this sprint.** Reducing
worker count would free ~5 GiB of RAM but wouldn't help the perceived-latency
problem (which is in Node, not Flask). If Redis pressure forces the issue later,
6 workers × 8 threads is safely sized for the p99 traffic seen.

## The cache lever — anonymous-page ISR

### Mechanism: Next.js ISR

`export const revalidate = 60` on the affected pages, with the SSR call's
personalization stripped so the render is stable for all anonymous visitors.

- **Chosen over Caddy `s-maxage` + cookie-conditional proxy cache** because the
  base Caddy build here has no cache module (Souin isn't installed) and the
  install-a-plugin-and-tune-a-cache-key path is a much larger change for the
  same latency win. Next.js ISR is in-process, zero infra changes, and the
  anonymous/authed split is enforced by the code path itself (SSR never reads
  cookies, so the cached HTML is definitionally the anonymous view).
- **Freshness: 60s revalidate.** Scribe's ingestion cycle is ~13 min, so 60s
  staleness is invisible to a reader. New user submissions and comments both
  fall inside the revalidate window.
- **Auth-cookie bypass is automatic**, not opt-in: the pages that cache do NOT
  call `auth()` / `cookies()` / `headers()` in the render path, so Next.js
  cannot serve a personalized page and then cache it. Client-side
  personalization (sign-in avatar, sign-out button, per-user UI in
  `ClientLayout`) already runs from `useSession()` and is unaffected — nav
  chrome swaps on hydration exactly as before.

### Scope

Cached (anonymous view, 60s):

| Route | Before | After |
|---|---|---|
| `/` | force-dynamic, `auth()`, `no-store` fetch | `revalidate = 60`, no auth, cached fetch |
| `/article/[slug]` | dynamic (via `headers()` + `searchParams`) | `revalidate = 60`; lang moved to client via `useSearchParams` |
| `/wiki/[slug]` | fetch-only cache (300s) | page-level `revalidate = 300` too |
| `/about` | static, no directive | `revalidate = 3600` |

Already cached correctly (untouched):

- `/sources`, `/library`, `/plants`, `/syndromes`, `/wiki` — all have `revalidate`.

**NOT cached (kept dynamic on purpose):**

- `/publish` — auth-required, user-personalized form (`'use client'` + `useSession`).
- `/quiz` — daily quiz, per-request payload with jitter.
- `/search` — client-side, per-query.
- `/library` authed views, and any `/api/*` POST route.
- SoC course pages (`Cache-Control: private, no-store` verified 2026-07-16) —
  this work is arc_stack only, does not touch that boundary.

### Known small regressions from stripping SSR personalization

- Homepage: authed users' initial paint no longer includes their own private
  articles in the SSR slot (`limit=1`). Client-side infinite scroll still fetches
  with the session cookie via the Next.js proxy, so private articles reappear on
  the second page onward. Net effect: at most one private article slides down
  one slot on first paint for authed owners.
- Article page: `X-Real-User-Agent` forwarding is dropped from the SSR fetch
  path. That header powered the analyzer-queue bot-gate at `/api/article/:id`.
  Since cached renders no longer hit the backend, the gate only matters on
  cache-miss (once per 60s per article). Some crawler-triggered enqueues will
  slip through; the analyzer's `analyzer:queued:{id}` NX-EX dedup absorbs them
  in a 6h window (main.py:650).

### Auth-bypass verification

Two curls, one with a session cookie header and one without, both hit the
homepage; both received `x-nextjs-cache: HIT` on the same cached HTML:

```
$ curl -I https://arc-codex.com/                          # anonymous
x-nextjs-cache: HIT
cache-control: s-maxage=60, stale-while-revalidate=...

$ curl -I -H "Cookie: __Secure-next-auth.session-token=…" https://arc-codex.com/
x-nextjs-cache: HIT
cache-control: s-maxage=60, stale-while-revalidate=...
```

That's the invariant: the SSR code path never reads cookies, so Next.js
cannot serve a personalized page and then cache it. Client-side hydration
(`ClientLayout`, `useSession()`) still swaps in per-user nav chrome on the
authed user's browser — verified by inspecting `/api/auth/session` and
`/api/get_feed`, both of which returned `cache-control: private, no-cache,
no-store` and pass the session cookie to Flask via `X-User-Id` in the proxy
route.

## Deploy notes

- Built via `docker compose build frontend` (Turbopack; ~12s compile, ~80s
  image export). ArticleView.tsx (new client wrapper) and page/article/wiki
  edits typecheck clean (`npx tsc --noEmit` — 0 errors).
- Deployed with `docker compose up -d --no-deps frontend`. **Do not use `up
  -d frontend` alone** — Compose tries to recreate the `gunicorn` dependency,
  which conflicts with the bare-metal gunicorn on port 5005 (the `arc.sh
  start` process). Recreation fails, and Compose leaves the frontend down.
  This bit us mid-deploy; recovered in ~15s with `--no-deps`.
- Suspense boundary requirement: pages that now cache must wrap
  `useSearchParams()`-using client components in `<Suspense>`. Applied to
  `FeedClient` on `/` and `ArticleView` on `/article/[slug]`. Without this
  the build fails with `useSearchParams() should be wrapped in a suspense
  boundary`.
